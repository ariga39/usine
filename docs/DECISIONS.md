# Usine technical decisions

This document records why the current boundary exists and when it should be reconsidered. [`DESIGN.md`](DESIGN.md) owns the current mechanics. A change to an active decision requires an authorized Issue/PR that names the superseded decision, the reason, and the impact on safety, authority, and recovery.

## Active decisions

| ID | Decision | Rationale and re-entry |
|---|---|---|
| D-001 | Optimize valid, valuable delivery outcomes and human attention, not internal artifact counts. | Prevent submission, test, agent-turn, or PR volume from becoming a proxy for accepted value. Reconsider only with evidence that the outcome/attention objective is insufficient. |
| D-002 | The top level is a deterministic coordinator, not a permanent Lead LLM. | Admission, ordering, recovery, permissions, and gates must be auditable; models do bounded semantic work only. |
| D-003 | Use TypeScript, Node 24, and a pnpm monorepo. | This matches the Codex, Drizzle, and Octokit ecosystem while making package ownership and isolated worktrees inspectable. Reconsider only for a measured platform/ecosystem constraint. |
| D-004 | Persist the minimum domain facts in SQLite/Drizzle and use deterministic reconciliation. Reserve stable identity/fence before each effect and record its observation afterward; do not add operation-index replay or a separate generic queue control plane. This supersedes the former PostgreSQL and DBOS direction and is amended by D-032 for Campaign reconciliation. | The current product has one local coordinator, one writer per Repository, and finite local capacity. D-032's Campaign frontier is owning domain state, not another scheduler. Re-enter a mature queue/workflow library only when multiple independent runners, durable delayed scheduling, measured polling/competition bottlenecks, or generic queue/timer code appear. |
| D-005 | Use Drizzle ORM/Kit with Node 24 `node:sqlite` transactions for domain persistence. | This removes unnecessary raw SQL and repository boilerplate while keeping schema, migrations, fences, effect identities, and state transitions explicit and atomic. Reconsider only with concrete consistency or scale evidence. |
| D-006 | Keep a task-oriented Coding Session port, `run(request) -> typed observation`, with exactly one statically selected official `@openai/codex-sdk`, bounded local Codex App Server, or qualified source-internal OpenCode2 adapter per opaque profile name. | The port hides provider lifecycle and prevents a general runtime surface. There is no fallback, registry, capability negotiation, automatic routing, general compatibility promise, or App Server/OpenCode2 task authority. Re-enter only when a real provider/runtime constraint cannot be solved within this port and can delete rather than duplicate lifecycle ownership. |
| D-007 | Use `ai` + `@ai-sdk/openai` only as an optional final role-output normalization adapter. | The coordinator may normalize schema-invalid provider prose, but the API key remains in the coordinator and the adapter never classifies, extracts generally, summarizes, or grants authority. Reconsider only for a specific bounded schema boundary. |
| D-008 | **Superseded by D-032.** The bounded serial `continue` path is the supported Task delivery leaf, not the complete product boundary. | Preserve the tested leaf and its evidence limits, but do not require an external guardian to supply and advance every Task. |
| D-009 | Bind Candidates, checks, reviews, approval attestations, and merge effects to one immutable exact SHA. | This prevents stale evidence, wrong-head merge, and agent prose from becoming delivery authority. |
| D-010 | Require a fresh reviewer with an explicit verdict; separate semantic approval from review-run completion. | Independent judgment remains meaningful, and Delivery can only project an existing approval. A GitHub-native approval, when required by ruleset, must use a capability distinct from the PR author/delivery identity. |
| D-011 | GitHub is the current forge and bounded read surface. Each Repository selects opaque `forgeProfile` and optional `githubReadProfile`; the host resolves separate capabilities and binds read MCP tools to the frozen Repository and authorized Goal/Task/Issue/PR artifact. D-032 amends the artifact scope; a per-Task GitHub Issue is not product authority. Campaign coordination admits bounded issue-less Campaign Tasks through the existing leaf; standalone Task admission still requires its matching Issue. | Credential separation and per-Repository policy are safety boundaries. Issue-less Campaign delivery does not fabricate an Issue or enlarge authority. Dependency acceptance reduction is delivered from durable Task facts: reviewed-only delivery satisfies only a cross-Repository dependency, while same-Repository work requires an accepted merged effect and uses its materialized merge head. Reducing accepted delivery into Outcome evidence, same-Repository overlap, and Planner replenishment remain outside this implemented slice. Read-profile resolution failure blocks the relevant activation; read credentials never become Forge credentials or public/durable data. |
| D-012 | **Superseded by D-026.** The old decision treated the reviewed-PR pause as the first product endpoint. | Preserve the historical identifier and supersession relationship, but use D-026 for current merge authority and terminal behavior. |
| D-013 | Use Codex sandbox and host permissions as the default isolation; do not make containers a prerequisite and never give workers delivery credentials. | Existing host isolation is sufficient for the current supported boundary. Re-enter container/VM isolation only when a real candidate cannot be safely handled by the current mechanism. |
| D-014 | Developing Usine itself follows Issue → branch/worktree → PR, with the first checkable state expressed as a small commit/checkpoint. | Git supplies recovery, visibility, ownership, and integration; it is not a progress proxy. See [`DEVELOPMENT.md`](DEVELOPMENT.md) for the development protocol. |
| D-015 | Canonical documents plus Issue/Git bootstrap are context-recovery truth; the orchestrator may use a larger context while workers and reviewers use task-sized context. | Context size reduces compaction pressure but never replaces durable principles. Reconsider only when artifact-first recovery demonstrably fails. |
| D-016 | Do not carry old implementations, old task trees, or historical designs into the new repository. | Clean-room work avoids compatibility-driven attention loss. External history may justify a decision but is not a production dependency. |
| D-017 | Require a fresh clean-room direction audit before a new canonical design is marked ready or merged; after the first complete vertical slice and before a major authority/scale expansion; and whenever repeated non-delivery, competing authority, or context loss makes the route uncertain. The finding must change task eligibility, not merely create backlog. | The orchestrator cannot independently prove that compaction or local optimization preserved the product aim. Re-enter this audit whenever one of those boundaries is crossed. |
| D-018 | Vite+ 0.2.9 is the unified workspace command/configuration surface: `vp fmt`, `vp lint`, `vp check`, `vp test`, and `vp pack`; the root test command remains the complete root-plus-workspace entry point. | This removes split formatter/linter/test/packaging wiring. `vp pack` is not a substitute for type checking. Reconsider only with a measured toolchain constraint. |
| D-019 | Each Issue/PR delivers one coherent module behavior; file movement, line count, and mechanical decomposition are not outcomes. | Delete or merge a seam only when its callers, evidence, and canonical boundary show that ownership has moved. |
| D-020 | Select work in this order: active falsifier or safety/authority defect; accepted-outcome critical path; representative real task; measured bottleneck; cleanup. | Local non-goals cannot waive a global falsifier. Re-enter the order only when evidence changes eligibility. |
| D-021 | Give each active behavior cluster a temporary design owner. Trigger independent design review for a new cluster/package/interface, three repeated policy copies, three repeated edits to one large file, or a falsified lifecycle. | Interface depth, test locality, and deletion need continuity across Issues; design review remains separate from correctness review. |
| D-022 | Once a module interface exists, tests replace implementation-coupled fixtures rather than layering more of them: interface behavior, adapter protocol, and a small CLI end-to-end set. | This keeps accidental transport details from becoming a permanent architecture. Remove old fixtures when new tests cover the claim. |
| D-023 | The six canonical product modules are real workspace packages: `@usine/task-authority`, `@usine/delivery-run`, `@usine/coding-session`, `@usine/candidate-workspace`, `@usine/quality-gate`, and `@usine/forge-delivery`. Their export graph is acyclic; runtime and CLI are composition roots, not a seventh behavior package. This supersedes the earlier option to keep modules inside fewer workspace packages. | Physical package boundaries provide inspectable ownership, test locality, and dependency evidence. Reconsider only if a current caller and measurable boundary failure justify merging or replacing a package. |
| D-024 | Introduce Effect 4 RC incrementally at untrusted durable-state decode boundaries, first for Task Authority's SQLite `TaskResult` decoder. Do not mechanically migrate the six packages, their Promise ports, Zod contract boundary, or Drizzle persistence. | The decode boundary gains validation and quarantine value; a wholesale service/layer rewrite would increase caller knowledge and migration cost. Re-enter per caller when Effect removes concrete duplicate validation, mapping, or lifecycle code. |
| D-025 | The persistent local server owns the Effect Scope, HTTP resources, Task fibers, durable re-entry, cleanup, and `AbortSignal` propagation. The implemented leaf CLI surface is `server health|snapshot`, `repository list|get`, `task list|get|history|watch|evidence|retry`, and `usage`; `register`/`submit` and explicit `retry` are mutation entries, while `inspect`/`status`/`follow` are compatibility aliases. Task `waiting` retains lease/capacity but does not auto-start. D-032 amends the server lifecycle with Campaign coordination. | Composition-root lifecycle belongs to the server; provider semantics remain in role adapters. Campaign entry and observation must extend the server-owned resource surface without turning the CLI or an external guardian into the scheduler. Task evidence and usage continue to read owning durable facts; restart never extends deadlines. |
| D-026 | **Supersedes D-012.** Admission freezes explicit `authorization.merge`. Without it, exact-SHA delivery ends at `reviewed_pr` and does not call merge. With it, Forge revalidates live PR, attestation, and approved SHA, then lets GitHub's merge endpoint be the final platform-policy gate before recording `merged`. | This preserves user-granted authority and makes ambiguous/refused effects non-authoritative. Broader merge policy remains deferred until more real installation, identity, ruleset, and refusal evidence exists. |
| D-027 | Persist one ordered, bounded, sanitized Task-local event stream; authoritative events are created in the owning Authority transaction, while external sinks accept only closed Coding Session/recovery observations. Process-local wait/subscribe is best-effort observation only. External observer/supervisor bridges are separate glue processes, not part of the Usine server or Task Authority; they use existing generic loopback resources/mutations and process-local subscribe invalidations, and reread current Task resources/history for correctness. | `TaskResult` remains the sole lifecycle authority. Bridges own best-effort wake delivery, agent-product configuration/lifecycle, coalescing/retry, and one bounded replaceable MCP session. No durable cursor, ledger, replay, acknowledgement, second scheduler, agent-session store, or Hermes-specific server API/fact/event/persistence is added. Disconnect/restart starts fresh; terminal transitions while offline may lose individual wakes. Webhook, MCP, and process state never prove completion. Re-enter only for an observed operator need that cannot be met by Task resources/history and can preserve this authority split. |
| D-028 | **Superseded in Campaign scope by D-032.** Direct standalone Task admission retains positive finite `USINE_ACTIVE_TASK_CAPACITY` (default `1`), same-ID idempotency, and over-capacity refusal. | Campaign proposals must wait durably outside active Task capacity so the coordinator, rather than an external submitter, can admit the next Ready Task. This does not authorize over-capacity launch or a distributed scheduler. |
| D-029 | Coding Session owns one versioned, host-local Session Archive per implementer/reviewer run. Store bounded atomic snapshots beneath the existing state root in a directory separate from SQLite; retain only a finite count. Expose metadata and opaque references through normal Task surfaces, and require a direct host-local CLI operation for one validated archive ID to export content. Never serve archive content through the unauthenticated loopback API. | Exact prompts, provider items, responses, normalized output, usage, and failures are useful recovery evidence but sensitive and non-authoritative. Archive truncation, write failure, and pruning must be observable without changing role, Candidate, review, delivery, or terminal authority. Re-enter only when a measured operator need requires a maintained storage or authenticated retrieval boundary that preserves this ownership split. |

| D-030 | Session Archive capture keeps the strict caller-owned authorized prompt/contract and explicitly projected provider evidence, plus a whitelist-only profile snapshot with a stable checksum; resolved host Repository facts, environment, credentials, transport metadata, and hidden configuration, including provider maps and model catalogs, remain excluded. The digest-only `configSha256` used in effective role evidence is separate from the archive snapshot checksum and never adds hidden configuration to the archive. Private bounded snapshots are read through no-follow descriptors with identity and integrity checks; corrupt entries do not hide valid archives. Archives have explicit completeness and bounded pruned tombstones. | The archive is intentionally sensitive recovery evidence, while its metadata/reference remains safe for normal Task surfaces and archive writes remain non-authoritative. Re-enter only for a measured retrieval need that preserves host-local ownership and finite storage. |

| D-031 | Keep OpenCode2 activation fail-closed and source-internal until Coding Session proves a host-enforced boundary. The current qualification is macOS Seatbelt through `/usr/bin/sandbox-exec`: a real deny-default profile must pass a preflight covering workspace reads, implementer/reviewer writes, external reads/writes, and inherited subprocess writes before the owned process starts. OpenCode permission rules are an additional provider policy, not isolation evidence; unexpected V2 asks are rejected and bounded. OpenCode2 has no built-in equivalent to Codex “Approve for me”; a future Usine-owned reviewer is not part of this decision. | The current managed macOS host rejects strict profile application, so its OpenCode2 activation remains disabled. Add another host family only with equivalent repeatable boundary evidence and an explicit update to the canonical supported-host claim; never replace this with a prompt, model refusal, permission label, container assumption, or process-state claim. |
| D-032 | **Supersedes D-008 and D-028 for product orchestration; amends D-004, D-011, and D-025 for Campaign scope.** The current product boundary is one bounded Campaign: a published Goal Contract authorizes an Outcome Tree and rolling Task frontier; deterministic coordination admits Ready Tasks through the existing delivery leaf, resolves each exact base when the Task becomes Ready, advances dependencies after accepted delivery, replenishes the frontier, and closes from Outcome evidence. An accepted dependency is proven from durable exact-SHA Task facts; reviewed-only delivery satisfies only cross-Repository dependencies, while same-Repository dependencies require an accepted merged effect. Forge Delivery materializes every accepted merge head in the registered local repository without changing checkout HEAD. The initial same-Repository policy remains serial through authorized merge; different Repositories may use available capacity concurrently. | A Repository-level trial proved that the leaf works only when a guardian manually decomposes, submits, and advances work. Durable planned/Ready records in SQLite are Campaign domain state, not a second generic queue control plane. Reconsider same-Repository overlap, a maintained workflow engine, or distributed runners only after current behavior and measured pressure justify them. |
| D-033 | Requirement Proxy and Planner are bounded semantic roles. Only user authority or a pre-delegated publication policy creates an immutable Goal publication; in the local-server composition, a host-owned publication anchor must corroborate the committed authority source. Planner output is an idempotent proposal with Outcome trace and no lifecycle authority. Rolling-wave planning is the default: freeze the accepted Outcome Tree, propose a bounded near-term frontier, and reactivate one Planner only on low watermark, invalidating evidence, or an incomplete empty frontier. | This restores autonomous task supply without a permanent Lead model or speculative full DAG. A model-writable contract, arbitrary source prose, or `authority.publish` cannot mint executable authority. The implemented Task `SessionRequest` must not be widened by passing fake Task Contracts; the first Spec/frontier caller owns its narrow structured role contract and may extract only proven shared provider lifecycle. |
| D-034 | Campaign evidence associates every admitted Task and semantic role invocation with one Goal version and Outcome. Aggregate uncached input, cached input, output, model/provider identity, elapsed time, review/repair cycles, replans, discarded proposals, human touches, and accepted deliveries from owning durable facts. | Cost and correction data must exist before another trial so capacity and self-improvement claims are measurable. Reusing Task usage facts avoids a parallel telemetry authority. |

## Selected dependencies

These are the deliberately narrow primitives behind the decisions; current ownership and usage are described in [`DESIGN.md`](DESIGN.md#5-behavioral-packages-and-composition).

- [Node 24 SQLite](https://nodejs.org/api/sqlite.html) for local transactions and file-backed durable facts.
- [Drizzle ORM and Kit](https://orm.drizzle.team/docs/kit-overview) for typed schema, queries, and code-first migrations.
- [Vite+](https://viteplus.dev/guide/) and its [migration/monorepo guidance](https://viteplus.dev/guide/migrate) for workspace commands and configuration.
- [OpenAI Codex SDK](https://developers.openai.com/codex/sdk/) for the official adapter; the local Codex App Server and qualified source-internal OpenCode2 adapter are peers behind the same port.
- [GitHub App authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app) and [Octokit](https://github.com/octokit/octokit.js#readme) for host-scoped Forge and read capabilities.
- [GitHub review approval rules](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews) as the reason platform approval and Usine semantic approval remain separate facts.
- Effect 4 RC for the selected decode and server lifecycle boundaries; Zod remains the external Task Contract boundary.
- Execa for narrow Git/project-command subprocess adapters; `ai` + `@ai-sdk/openai` only for optional final role-output normalization.
- Vite+ tests for public behavior, including SQLite independent-connection and hard-kill recovery fixtures where applicable.

## Deferred options and re-entry

Deferred means “do not reserve implementation for it now,” not “never.”

| Option | Current posture | Re-entry condition |
|---|---|---|
| ACP runtime protocol | Deferred | The Codex adapter cannot provide required turn observation/cancellation, or a stable ACP implementation can delete substantial adapter complexity. |
| OpenCode runtime adapter | Disabled except for the qualified source-internal OpenCode2 adapter described in D-031 | Re-enter a supported-provider claim only after repeatable host-boundary evidence covers both roles, filesystem/process escape attempts, permission asks, cancellation, and cleanup on each claimed host family. |
| Stop hook | Optional non-authoritative optimization | Recovery is correct and measured data shows a meaningful latency/token benefit; it must not create activation, fence, or completion authority. |
| Broader automatic merge policy | Narrow authorized merge selected; broader policy deferred | More real pilots establish GitHub App identity/permission, repository ruleset, and platform-refusal behavior without creating a merge service, queue, or concurrent writer model. |
| Gitea or another forge | Deferred | GitHub API, private-repository capability, cost, or contributor workflow becomes a measured limitation. |
| Durable queue/workflow engine or distributed runner | Deferred | Multiple independent runners, durable delayed scheduling, database polling/competition, or generic queue/timer/DAG code becomes a measured need; prefer a maintained primitive. |
| Container or lightweight VM provider | Deferred | Codex sandbox/host permissions cannot isolate a real candidate, or project dependencies require a disposable OS image. |
| Mem0/vector/session memory | Deferred | Artifact-first bootstrap repeatedly loses reusable knowledge in real recovery and ordinary files/indexes cannot solve it. |
| Dynamic model router | Deferred | Static role/project policy creates sustained, quantified quality or subscription-capacity loss. |
| Automatic lesson promotion | Deferred | Repeated Campaign evidence and an evaluator show that a proposed rule, skill, checker, or routing change improves held-out outcomes without expanding authority. |
| Exhaustive hostile Git/DB catalog validation | Not on the default route | The deployment threat model or a real incident proves fresh-checkout, SHA/ancestry, or migration checks insufficient. |
| Web dashboard | Deferred | Minimal operator output fails a documented daily blocker-localization need and the missing query is known. |
| OpenAI Agents SDK `SandboxAgent`/`codexTool` | Donor/deferred | A non-Codex agent loop, handoff, or provider-neutral sandbox is required and can delete existing Delivery Run/Coding Session ownership rather than create a second loop. |
| Herdr host/observer | Production path removed | Operator observation becomes a measured bottleneck and an internal Coding Session adapter can remove code without treating panes or transcripts as completion evidence. |
